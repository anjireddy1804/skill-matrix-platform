# Skill Matrix Terraform Foundation

This directory contains the Terraform foundation and application runtime for the `skill-matrix` Demo environment. It creates remote-state bootstrap, VPC networking, security groups, backend ECR/RDS/secrets, ALB/ECS runtime resources, and private Angular hosting through S3 and CloudFront. CI/CD and custom-domain services remain intentionally deferred.

> **DEMO ENVIRONMENT — DUMMY / NON-CONFIDENTIAL DATA ONLY**
>
> Do not use real employee information, client-sensitive information, production database dumps, production credentials, or sensitive personal information.

## Architecture foundation

```text
VPC: 10.20.0.0/16

Public AZ1              Public AZ2
10.20.1.0/24            10.20.2.0/24
Future ALB/ECS          Future ALB/ECS
        |                    |
        +---- Internet Gateway

Private DB AZ1          Private DB AZ2
10.20.11.0/24           10.20.12.0/24
        |                    |
        +------ Future RDS
```

The Demo network uses two availability zones selected dynamically from the AWS region. Public subnets have a default route through one Internet Gateway and are reserved for the future ALB and ECS tasks. Private database subnets have no default Internet route and are reserved for future RDS.

There is deliberately no NAT Gateway. Future Demo ECS tasks will use public subnets with restrictive security groups and `assign_public_ip = true` to avoid recurring NAT Gateway cost. This is Demo-specific; future production designs may use private ECS subnets with NAT Gateway or VPC endpoints.

The security-group chain is:

- ALB: public TCP 80 ingress and ECS application-port egress.
- ECS: application port 8080 ingress only from the ALB security group; unrestricted outbound traffic for the Demo public-subnet strategy.
- RDS: MySQL TCP 3306 ingress only from the ECS security group.

No IAM OIDC, CloudWatch alarms, CloudTrail, Budget, WAF, Route53, ACM certificate, or ECS autoscaling is created here.

## Container and database foundation

```text
ECR backend repository
                  ^
                  |
        Future CI/CD

Private DB Subnets
                  |
                  v
          RDS MySQL
                  ^
                  |
                ECS SG
                  |
         Future ECS
```

The ECR repository is named from the project and environment, uses AES-256 encryption, scan-on-push, immutable tags, and retains the most recent 10 `sha-` or `commit-` tagged images. Untagged images expire after one day. CI/CD should publish commit SHA tags rather than relying only on `latest`.

RDS uses MySQL 8, a configurable economical instance class, 20 GiB GP3 storage by default, seven-day backups, and a single AZ. It is not publicly accessible, uses only the private DB subnets, and allows MySQL access only from the ECS security group. Multi-AZ is intentionally deferred for Demo and can be enabled for Prod later.

The RDS master password is managed by RDS through Secrets Manager. Terraform does not accept or output a plaintext database password. The application JWT secret is generated by Terraform and stored in Secrets Manager; only its ARN is output. Terraform state is sensitive and must be protected by the bootstrapped encrypted, versioned S3 backend.

After this foundation is deployed, RDS exists and the ECR repository is initially empty. A later step must build and push the backend Docker image before creating ECS. When the future Spring Boot service starts, Flyway will connect to RDS and apply pending migrations during application startup.

Future ECS environment mapping:

```text
SPRING_PROFILES_ACTIVE=prod
SPRING_DATASOURCE_URL=jdbc:mysql://<rds-endpoint>:3306/skill_matrix_db
SPRING_DATASOURCE_USERNAME=<rds username>
SPRING_DATASOURCE_PASSWORD=<value from the RDS master secret>
APP_JWT_SECRET=<value from the JWT secret>
```

## ALB and ECS runtime

The internet-facing ALB listens on HTTP port 80 and forwards to an IP target group on backend port 8080. The target group checks `/actuator/health` and expects HTTP 200. HTTPS is intentionally deferred until the future CloudFront/ACM work.

The Demo ECS cluster uses Fargate with 512 CPU units, 1024 MiB memory, and one desired task by default. Tasks use `awsvpc` networking in the existing public subnets with `assign_public_ip = true`, attach only the ECS security group, and use Fargate platform `LATEST`. This avoids NAT Gateway cost for Demo; production should use private ECS subnets with NAT Gateway or VPC endpoints.

The ECS execution role uses the AWS-managed `AmazonECSTaskExecutionRolePolicy` for image pulls and log delivery, plus narrowly scoped `secretsmanager:GetSecretValue` access to the RDS and JWT secret ARNs. The separate application task role has no AWS API permissions because the current application does not require them.

Backend logs use `/ecs/skill-matrix-demo-backend` with the `awslogs` driver and seven-day retention by default.

## Initial deployment sequence

The first infrastructure deployment uses `create_ecs_service = false`. Phase A creates the network, security groups, ECR, RDS, Secrets Manager secrets, ALB, ECS cluster, IAM roles, and log group, but no ECS task definition or service. The ECR repository is empty initially.

In Phase B, build and push the backend Docker image using an explicit immutable commit SHA or version tag. The commands are intentionally documented only; do not put registry credentials in Terraform files:

```text
docker build -t <repository-url>:<commit-sha> backend
aws ecr get-login-password --region ap-south-1 | docker login --username AWS --password-stdin <registry>
docker push <repository-url>:<commit-sha>
```

In Phase C, set `backend_image_tag` to the pushed tag and set `create_ecs_service = true`, then review and run Terraform plan/apply manually. The task starts, connects to RDS, Flyway reads `classpath:db/migration` and applies pending migrations, and the ALB health check validates `/actuator/health` after startup. A separate migration task is not needed for Demo.

The task definition defaults to `latest` only to keep the disabled bootstrap structurally configurable. Enabling the service requires an explicit non-`latest` image tag. Future GitHub Actions should publish commit SHA tags and own task-definition revisions/service rollouts. Terraform narrowly ignores only the ECS service `task_definition` field so later CI/CD deployments are not rolled back by routine infrastructure plans.

The ALB still incurs charges once created. With `create_ecs_service = false`, no ECS task is running and therefore no Fargate task charge is incurred; the ALB, RDS, ECR storage, Secrets Manager, and CloudWatch Logs costs remain subject to usage and AWS pricing.

## Frontend delivery

```text
                                                 CloudFront
                                                /          \
                                           /            \
                                  S3 Angular      /api/*
                                                                          |
                                                                          v
                                                                         ALB
                                                                          |
                                                                          v
                                                                  ECS Fargate
                                                                          |
                                                                          v
                                                                   RDS MySQL
```

The frontend bucket is private: all public access is blocked, ACLs are disabled, and CloudFront uses Origin Access Control with SigV4 signing. The bucket policy grants only `s3:GetObject` to `cloudfront.amazonaws.com` when `AWS:SourceArn` matches this distribution. S3 website hosting is not enabled.

CloudFront uses the existing ALB DNS name as an HTTP custom origin for `/api/*`. The API path is preserved unchanged, so `/api/v1/auth` reaches the ALB and Spring Boot as `/api/v1/auth`. API requests redirect viewers to HTTPS, allow the REST methods required by the application, disable caching with the managed `Managed-CachingDisabled` policy, and use the managed `Managed-AllViewerExceptHostHeader` origin-request policy so Authorization headers, query strings, and cookies are available to the backend.

The default behavior serves the S3 origin over HTTPS with the managed optimized cache policy. A small CloudFront Function is attached only to this default behavior. It leaves `/api/*` and requests with file extensions unchanged, and rewrites other Angular client-side routes such as `/login`, `/admin`, `/lead`, and `/technician` to `/index.html`. This avoids distribution-wide 403/404 custom error responses that could incorrectly turn genuine API errors into Angular HTML.

Demo uses the default `*.cloudfront.net` certificate and `PriceClass_100`. No custom domain, Route53 record, ACM certificate, or WAF is created. The public application URL is the `application_url` output. CloudFront IPv6 is enabled by default.

Terraform owns the frontend bucket, policy, OAC, distribution, and function only. It does not create `aws_s3_object` resources for build artifacts, CloudFront invalidations, or deployment credentials. Future CI/CD owns `frontend/dist/skill-matrix-ui/browser` artifacts, should sync them to the output bucket, and should invalidate `/*` after deployment.

The current successful Angular build contains `index.html` directly under `frontend/dist/skill-matrix-ui/browser`:

```text
cd frontend
npm ci
npm run build
aws s3 sync dist/skill-matrix-ui/browser s3://<frontend_bucket_name> --delete
aws cloudfront create-invalidation --distribution-id <cloudfront_distribution_id> --paths "/*"
```

These AWS commands are documentation only and are not executed by Terraform in this step.

Because the browser uses one CloudFront origin for both frontend and `/api/*`, Angular keeps its relative `/api/v1` base URL and does not receive the ALB DNS name. Configure `cors_allowed_origins` with the CloudFront `application_url` before enabling ECS. The clean sequence is: create the frontend/CloudFront layer with ECS disabled, read `application_url`, set that URL in `cors_allowed_origins`, then enable ECS. Do not use `*`.

## Cost notes

This step introduces planning-level charges for the RDS instance, RDS storage and backups, ECR image storage, and two Secrets Manager secret containers. Demo defaults intentionally avoid Multi-AZ RDS, read replicas, Performance Insights, enhanced monitoring, NAT Gateway, and excessive storage.

## Bootstrap process

The bootstrap uses local Terraform state initially and creates a globally unique, account-specific S3 state bucket with public access blocked, ownership controls, AES-256 server-side encryption, versioning, and old noncurrent-version expiry.

Terraform 1.10 or later supports native S3 state locking with `use_lockfile = true`; no DynamoDB lock table is created.

```text
cd infrastructure/terraform/bootstrap
terraform init
terraform fmt
terraform validate
terraform plan -var-file=terraform.tfvars.example
```

After the state bucket is reviewed and created by the user, copy its output into a local `backend.hcl` based on `backend.hcl.example`. Do not commit `backend.hcl`.

## Demo initialization

```text
cd infrastructure/terraform/environments/demo
terraform init -backend-config=backend.hcl
terraform fmt
terraform validate
terraform plan -var-file=terraform.tfvars.example
```

The backend configuration is intentionally partial so the state bucket name is not hardcoded before bootstrap. Credentials should be supplied through the normal AWS credential chain, never in Terraform files.

## GitHub Actions CI/CD

The repository workflows use GitHub OIDC rather than long-lived AWS access keys:

```text
                                                        GitHub Demo
                                                                 |
                         +--------------+--------------+
                         |              |              |
                 Terraform       Backend        Frontend
                         |              |              |
                         v              v              v
                        AWS            ECR             S3
                                                                  |              |
                                                                  v              v
                                                                 ECS         CloudFront
```

The reusable `github_oidc` module creates the GitHub OIDC provider and two Demo roles:

- Terraform role: manages the AWS service families represented by this repository and can access the exact remote-state bucket when `terraform_state_bucket_name` is configured. It is not `AdministratorAccess`.
- Application role: pushes only to the backend ECR repository, deploys the named ECS service, passes only the ECS execution/task roles, syncs only the frontend bucket, and creates invalidations only for the CloudFront distribution.

The trust policy requires audience `sts.amazonaws.com` and the exact GitHub Environment subject:
`repo:VenkataJanga/skill-matrix-platform:environment:demo`. Deployment jobs therefore use `environment: demo`. Configure environment protection/approval in GitHub before using deploy workflows. If a workflow later stops using the Environment and uses a branch subject instead, the IAM trust policy must change to match the token subject. The `github_branch` variable controls workflow branch conventions and is `Demo`; it does not replace the Environment-based trust condition.

If the AWS account already contains `https://token.actions.githubusercontent.com`, set `create_github_oidc_provider = false`, provide `existing_github_oidc_provider_arn`, and do not attempt to create a duplicate provider. If the existing provider is unmanaged, it can be imported into the Terraform state during a separately reviewed bootstrap process.

### Workflow behavior

Terraform changes under `infrastructure/terraform/**` trigger format, initialization, validation, and plan on trusted Demo PR/push contexts. Fork PRs do not receive AWS OIDC credentials. A separate `workflow_dispatch` input explicitly enables Terraform apply; normal pushes never apply and no workflow runs destroy.

Backend changes under `backend/**` trigger Java 21, Maven `clean verify`, Docker build, immutable `${GITHUB_SHA}` ECR push, task-definition image rendering, ECS service update, and service-stability wait. The backend workflow does not run Terraform.

Frontend changes under `frontend/**` trigger Node 20, `npm ci`, `npm run build`, and sync of the verified Angular browser artifact:

```text
frontend/dist/skill-matrix-ui/browser
```

The workflow syncs only that directory to the configured frontend bucket with `--delete`, then invalidates `/*` on the exact CloudFront distribution. Terraform does not manage Angular objects or invalidations. Node 20 is selected because no repository Node version is defined and it is compatible with this Angular 17 project.

### Required GitHub Environment variables

Create a protected GitHub Environment named `demo` and configure these non-secret variables from Terraform outputs:

| Variable | Source |
|---|---|
| `AWS_REGION` | `aws_region` / `ap-south-1` |
| `TERRAFORM_ROLE_ARN` | `github_terraform_role_arn` |
| `APPLICATION_ROLE_ARN` | `github_application_role_arn` |
| `TF_STATE_BUCKET` | Bootstrap `state_bucket_name` output |
| `CREATE_ECS_SERVICE` | Optional; defaults to `false`, set `true` only after an image exists |
| `BACKEND_IMAGE_TAG` | Optional; explicit immutable image tag required when ECS is enabled |
| `CORS_ALLOWED_ORIGINS_JSON` | Optional JSON list; set to `["https://<cloudfront-domain>"]` before enabling ECS |
| `ECR_REPOSITORY` | `ecr_repository_name` |
| `ECS_CLUSTER` | `ecs_cluster_name` |
| `ECS_SERVICE` | `ecs_service_name` after ECS is enabled |
| `ECS_TASK_DEFINITION_FAMILY` | `ecs_task_definition_family` |
| `ECS_CONTAINER_NAME` | `ecs_container_name` (`backend`) |
| `FRONTEND_S3_BUCKET` | `frontend_bucket_name` |
| `CLOUDFRONT_DISTRIBUTION_ID` | `cloudfront_distribution_id` |
| `APPLICATION_URL` | `application_url` |

The workflows require no GitHub secret for AWS credentials, no PAT, no database password, and no JWT secret. AWS runtime secrets remain in Secrets Manager. Standard checkout uses the built-in `GITHUB_TOKEN`.

### First-time setup

1. Review and manually apply the bootstrap Terraform to create the state bucket.
2. Configure the Demo backend with that bucket and initialize the Demo Terraform root.
3. Set `terraform_state_bucket_name` to the bootstrap output and deploy infrastructure with `create_ecs_service = false`.
4. Capture the Terraform outputs and configure the protected GitHub `demo` Environment variables above.
5. Create and push the `Demo` branch manually; it does not exist automatically.
6. Build and push the first backend image with a commit SHA tag, or use the backend workflow after the service exists.
7. Set `backend_image_tag` to that exact SHA and set `create_ecs_service = true`; review and manually apply Terraform once.
8. Set `cors_allowed_origins` to the `application_url` output and apply the CORS change if it was not included in the ECS enablement plan.
9. Deploy the frontend through the frontend workflow and validate the CloudFront application URL.
10. Use the backend and frontend workflows for subsequent application releases.

Terraform owns ECS service infrastructure and the task-definition baseline. GitHub Actions owns the current backend image and task-definition revision. The ECS module ignores only the ECS service `task_definition` field, so routine Terraform runs do not roll the service back over a CI/CD deployment. CPU, memory, IAM, networking, secrets, logging, and desired count remain Terraform-managed.

Terraform state contains sensitive infrastructure metadata and generated secret material. Protect the remote state bucket and do not commit `terraform.tfvars`, backend configuration, or generated workflow artifacts.
